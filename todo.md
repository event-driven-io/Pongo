## Notes

- Driver type planned as `SQLite:cloudflareDurableObjectSQLite`, matching the existing SQLite driver type convention while keeping Cloudflare explicit in the driver name.
- The public Dumbo option requires `storage: DurableObjectStorage`; raw `SqlStorage` is not supported because every constructed driver must support transactions.
- `storage` means the full Cloudflare Durable Object storage object, usually `ctx.storage`; `sql` means only `ctx.storage.sql`.
- Execution derives `SqlStorage` internally from `storage.sql`; the client does not expose a degraded execution-only construction mode.
- Transactions must not emit `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, or `RELEASE` through `ctx.storage.sql.exec()`.
- Full transaction support uses `DurableObjectStorage.transaction(async () => ...)`.
- Do not use `DurableObjectStorage.transactionSync()` in this driver implementation. The Miniflare PoC validated async `storage.transaction(async () => ...)`, and the public Dumbo/Pongo transaction API must stay async.
- Existing package `./cloudflare` exports should be enough; package export maps likely do not need changes.
- Runtime tests use `@cloudflare/vitest-plugin`, a tiny real test Durable Object class, generated Wrangler binding types, and `runInDurableObject()` to execute Dumbo against real `state.storage`. Do not use fake `DurableObjectStorage` or custom SQL parsers in integration tests.
- Proper Cloudflare test setup means conventional colocated `*.int.spec.ts`/`*.e2e.spec.ts` files under the Dumbo/Pongo `durableObject` paths, path-based ownership in the shared root `vitest.cloudflare.config.ts`, `tsconfig.cloudflare.json`, and ESLint configuration, Dumbo's `packages/dumbo/wrangler.durable-object-sqlite.jsonc`, and full Wrangler-generated runtime/binding types in `packages/dumbo/worker-configuration.d.ts`.
